# Независимая проверка аналитики

Тесты соответствия текущим эвристикам не являются эталоном качества коучинга. Проверка разделена на пять уровней: извлечение фактов; оценка выбора; соответствие текста доказательствам; полезность упражнения; изменение поведения. Успех одного уровня не заменяет следующий.

## 1. Корпус и экспертная разметка

Создать версионированный manifest реальных replay: content hash, источник, match ID, patch/build, игроки/команды, уровень/качество роли, доступность записи клиента, интервалы полного покрытия, ограничения. Синтетические fixtures имеют отдельный `dataset_kind=synthetic` и никогда не попадают в статистику точности на людях.

Два независимых эксперта размечают спорные ключевые эпизоды, затем третий или согласованный разбор разрешает расхождения. Разметчик не получает verdict системы до фиксации собственного решения. Отбор включает правильные решения с плохим исходом, неправильные с хорошим, несколько допустимых альтернатив, технически невозможные действия и недостающие данные. Отдельно набираются непримечательные эпизоды без смерти: иначе нельзя измерить пропущенные ошибки и false alarm rate.

### Проход A: извлечение и наблюдаемость

Сверить raw events и поля с клиентом на ограниченных интервалах: identity, time mapping, паузы, собственные ресурсы, наблюдаемость угрозы, предмет/действие/ограничения. Отметить точность и то, что клиент тоже не позволяет удостоверить. Полный replay и командный POV сверяются отдельно. Наличие камеры не доказывает внимание.

### Проход B: решение без будущего

Эксперт видит только разрешённый префикс до выбора и минимальный token выбранного действия, если он нужен для оценки. Для размечаемого бездействия показывается только закрытое окно возможности без последующего воздействия. Сначала фиксируются границы, знания, цели-гипотезы, feasibility и допустимые оценки; затем аргументы. Если окно нельзя отделить от outcome, это причина неприменимости пилота.

### Проход C: исход и объяснение

После фиксации и хеширования B открывается продолжение replay. Оно используется для отдельного описания результата и проверки извлечения. Эксперт не переписывает B из-за результата. Если вскрылся дефект данных до выбора, создаётся новая версия annotation с явной причиной и повторной слепой проверкой; это не скрытая коррекция label.

### Проход D: текст и упражнение

Проверить, следует ли каждый claim из cited evidence, совпадают ли verdict/заголовок/совет, понятны ли неизвестные, выполнимо ли упражнение. «Полезно» от пользователя не доказывает истинность вывода. «Не согласен» требует разбора, но не автоматической отмены фактов.

## 2. Формат annotation record

Один JSONL record на `(decision_id, annotator_id, pass, version)`. Поля `null` допустимы только с причиной, а не как молчаливое отсутствие разметки.

```json
{
  "schema_version": "foresight.annotation.v1",
  "dataset_kind": "template_only",
  "decision_id": null,
  "replay_hash": null,
  "patch": null,
  "annotator_id": null,
  "annotation_version": 1,
  "pass": "decision_blinded",
  "input_hash": null,
  "outcome_visible": false,
  "system_verdict_visible": false,
  "boundary": {"earliest_tick": null, "latest_tick": null, "status": "unresolved"},
  "facts_checked": [],
  "available_actions": [],
  "goal_hypotheses": [],
  "criterion_id": null,
  "acceptable_verdicts": [],
  "decisive_evidence_ids": [],
  "unknowns": [],
  "excluded_alternatives_and_reasons": [],
  "rationale": null,
  "adjudication_status": "unreviewed"
}
```

Пустой шаблон не является готовой разметкой. Validators требуют непустые IDs, проверенные hash, допустимый pass и обязательные ответы для завершённой записи. Каждый action размечается как feasible/infeasible/unknown со ссылками; каждому fact — correct/incorrect/unverifiable и available/not_available/unknown. `acceptable_verdicts` может быть множеством: принудительный единственный «правильный ответ» искажает реальные альтернативы.

## 3. Разделение выборок

- **Development:** разработка извлечения, критериев, промптов и примеров; можно анализировать ошибки.
- **Locked holdout:** ни те же матчи, ни те же target players, ни их дубликаты/clips, ни примеры из retrieval/training. Публикуется manifest split и проверка пересечений.
- **Patch transfer:** более поздний или отдельно выбранный patch/build; не смешивать с обычным holdout. Пройденный старый патч не включает новый автоматически.
- **Within-player longitudinal:** для проверки привычки по времени один и тот же игрок необходим; это отдельный эксперимент, не доказательство обобщения на новых игроков. Периоды не пересекаются и фиксируются до просмотра результатов.

У multiplayer-матчей есть общие участники. Строгий player-disjoint split по всем десяти участникам требует анализа связных компонент графа player↔match; если граф сливается и такой split невозможен, это явно ограничивает заявляемую независимость. Минимальный target-player-disjoint split не называть all-player-disjoint. Нельзя разнести один матч по train/test через разных участников.

Holdout открывается для финальной проверки версии. После настройки на его ошибках он становится development; для следующего сильного заявления нужен новый закрытый набор. Cached LLM outputs, экспертные исправления и учебные рекомендации также проверяются на пересечения.

## 4. Метрики и знаменатели

| Уровень | Метрика | Знаменатель и смысл |
|---|---|---|
| Факты | wrong factual values; time error; identity/visibility violations | Все независимо проверенные факты соответствующего типа; раздельно по capabilities |
| Discovery | opportunity recall | Все релевантные возможности на вручную просмотренных интервалах, не только кандидаты системы |
| Обвинения | false discovery among accusations | Неподдержанные экспертами error labels / все выданные error labels |
| Обвинения | false positive rate | Ошибочно обвинённые / все экспертные non-error случаи |
| Охват | assessment coverage | Оценённые / подтверждённо eligible; unknown eligibility показывать отдельно |
| Отказ | warranted abstention и missed assessable cases | Экспертно подтверждённые причины отказа; избыточные отказы на достаточных данных |
| Вердикты | agreement with acceptable verdict sets | Eligible expert-reviewed эпизоды, с разбиением по классу/патчу/качеству |
| Текст | unsupported material claims | Существенные утверждения без достаточного основания / все существенные утверждения |
| Коучинг | comprehension/actionability | Ответы пользователей + экспертная проверка выполнимости; не число лайков |
| Поведение | target behavior rate и coverage shift | Сопоставимые opportunities в независимых периодах, с baseline и counterexamples |

Показывать числитель, знаменатель и интервал неопределённости. Возможности внутри матча/игрока коррелируют: интервалы считать с кластеризацией или явно описанной моделью зависимости, а не как тысячи независимых бросков монеты. N матчей, N игроков и N решений — разные числа.

## 5. Gates выпуска

Пороговые значения ниже — предложенная политика первого пилота, а не достигнутые результаты и не законы статистики. Их фиксируют до закрытой оценки; если данных мало, публикация точности остаётся заблокированной.

**Gate A — контракты.** Все обязательные структурные и metamorphic cases ниже проходят. Ноль известных нарушений hidden/future boundary. Отсутствующее обязательное поле даёт abstention. Оценщик работает и без LLM/видео.

**Gate B — реальные данные.** Для каждого обязательного capability есть raw/client proof в scope пилота, включая отрицательные/пограничные случаи. Ноль неустранённых критических ошибок identity/time/visibility в проверенном наборе. Это не заявление о нулевой вероятности ошибки вне набора.

**Gate C — оценка решений.** Предварительная целевая политика: односторонняя верхняя 95% граница доли ложных обвинений ≤5%; нижняя граница coverage ≥30% внутри заранее фиксированного scope; отдельно отчёт discovery recall и избыточных отказов. Scope нельзя сужать задним числом для прохождения порога. Если обвинений или независимых кластеров недостаточно для честного интервала, не заявлять достижение 5%. Ноль ошибок в нескольких примерах недостаточен. `confirmed_error` получает отдельный срез проверки; если он не подтверждён, этот label остаётся выключен.

**Gate D — объяснение.** Нет известных неподдержанных существенных обвинений или численных контрфактических обещаний в выпускной выборке. Противоречивый заголовок/текст блокирует карточку или заменяется шаблоном. Проверка проводится на фактическом render, включая короткие заметки и fallback, а не только на DTO.

**Gate E — польза.** Малый пользовательский пилот проверяет, могут ли игроки своими словами назвать выбор, доказательства и упражнение. Наблюдение изменения поведения оформляется отдельно; положительная динамика не доказывает причинный эффект тренера. Для такого заявления нужен отдельный дизайн сравнения с контролем/рандомизацией и учёт отбора/регрессии к среднему.

Не назначать произвольный общий объём вроде «20 матчей достаточно». Сначала extraction calibration batch для поиска ошибок, затем pilot estimates для расчёта необходимого числа независимых матчей/игроков и классов. Закрытая выборка не используется для такого тюнинга.

## 6. Обязательные acceptance cases

| ID | Воздействие / условие | Ожидание |
|---|---|---|
| T01 | Добавить/изменить события строго после decision cutoff | Input, boundary из prefix resolver, assessment и decision claims неизменны; outcome может измениться |
| T02 | Переместить скрытого врага, сохранив историю наблюдений | Те же input/assessment/claims; world view другой |
| T03 | Изменить end-of-fight gold/deaths при одинаковом префиксе | Ни verdict, ни объяснение выбора не меняются |
| T04 | Удалить обязательное поле readiness/control/visibility | Unknown + reason/abstention, не false/0/default alive |
| T05 | Добавить будущий ward с повторно использованным index | Прошлый lifecycle и visibility неизменны |
| T06 | Ward до horn; удаление не попало в replay | Учитывается начальное состояние; неизвестный конец/censoring, не выдуманный lifetime |
| T07 | Запрос между кадрами, gap, пауза, конец записи | Возраст/неопределённость явны; нет ложного observed_not_visible |
| T08 | Никогда не виденный enemy или потерянный entity | Never_observed/unknown; не точные «N секунд пропал» и не исключение врага из roster |
| T09 | Illusion/clone/entity replacement/slot mapping | Stable player mapping и разные entity generations; неизвестность блокирует зависимые оценки |
| T10 | Хорошее решение, плохой outcome | Сохраняется good/acceptable по blinded rubric |
| T11 | Плохое решение, хороший outcome | Ошибка не исчезает из-за удачного исхода |
| T12 | Два выполнимых варианта с существенными tradeoffs | Reasonable_options; нет выдуманного единственного оптимума |
| T13 | Предмет готов, но применение блокировано | Не обвинять за неприменение; prerequisite evidence видны |
| T14 | Предмет выполним, но сохранение имеет разумное основание | Нет автоматической ошибки из readiness |
| T15 | Неопределённый порядок same-tick событий/окно реакции | Abstain, если verdict зависит от порядка |
| T16 | Два решения в одну секунду | Разные IDs, отдельные notes/evidence; дедуп только по identity |
| T17 | Убрали death/outcome-based selection | Реестр всех возможностей сохраняет хорошие, непойманные и неоценённые решения |
| T18 | LLM поменяла verdict, добавила число или новый causal claim | Reject + deterministic fallback; HTML согласован |
| T19 | Повторно проанализирован тот же match set | Revision того же baseline; не progress |
| T20 | Роль/патч/качество/criterion изменились либо исчез детектор | Incomparable/insufficient/rebaseline; не resolved |
| T21 | 5 матчей с benchmarks, нужная метрика в одном | Denominator=1, не HIGH по 5 матчам |
| T22 | Короткая жизнь полезного варда / долгий бесполезный | Lifetime не устанавливает utility; outcome evidence отдельно |
| T23 | Replay/LLM/клип/каталог рекомендаций недоступен | Честное состояние; оставшиеся доказательства доступны; нет вымышленных ссылок |
| T24 | Переключить UI на полный replay | Вид изменился, assessment hash прежний |
| T25 | Видимость команды известна, POV/внимание нет | Текст «доступно команде», не «ты видел/проигнорировал» |
| T26 | Принцип есть, но его предусловия не доказаны | Он не превращается в применимый criterion или обвинение |
| T27 | Изменить parser/model/criterion version | Новый cache/run key; несовместимый старый результат не переиспользуется |
| T28 | Контекст существенно изменился внутри окна без активации | v1 abstain; конечный snapshot не объясняет раннее действие |
| T29 | Есть только лог successful activation, нет command attempts | Нет обвинения в отсутствии попытки/намерении сохранить |
| T30 | Incident index меняет смерть/результат при прежних наблюдениях | Независимые opportunity IDs, boundary/cutoff и assessment неизменны |
| T31 | Team visibility есть, конкретный reaction cue субъекту не подтверждён | Нет подтверждённой ошибки пропущенной реакции |

Инварианты T01–T03 сравнивают канонические DTO/claims, а не случайную строку LLM. Для явного действия граница — commit; для отсутствия активации — action_observation_end проверенного окна. Внутри окна сохраняются тот же ActionObservation и статус пригодности; изменение самого действия создаёт другой объект оценки. Knowledge cutoff шага остаётся его началом: более поздние данные не добавляют аргументы предпочтения. Отдельно проверить успешную активацию: её последствия (например cooldown) не должны отклонять пример как «контекст изменился». Для текста используется фиксированный input/model/cache или шаблон; evaluator не должен менять смысл при другом seed генерации.

## 7. Пакет независимой проверки Astro

Передать diff, версии контрактов/механик, raw replay hashes, manifest split, полный ledger, blinded annotations, результаты тестов, error analysis, отклонённые LLM ответы и отрендеренные реальные карточки. Astro проверяет не только несколько удачных демонстраций, но и abstentions, контрпримеры, исключённые opportunities и происхождение критериев.

Результат проверки: `accept within scope`, `request changes` или `data validation blocked` с конкретными основаниями. Нельзя принять неподтверждённую аналитику только потому, что сборка и unit tests зелёные.
