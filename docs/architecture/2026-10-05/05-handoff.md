# Передача в реализацию Sol и последующая проверка Astro

Этот файл — задания для следующих этапов. В текущем этапе продуктовые исправления не выполнялись. Работа сабагентов ограничивалась аудитом и проверкой архитектуры, а не параллельной реализацией.

## Порядок изменений

### S0. Ограничить недоказанные выводы

**Цель:** существующий продукт перестаёт выдавать известные ложные обвинения до появления нового evaluator.

Изменения: `scoring.py`, `coach/info_state.py`, `episode_note.py`, `moment_prompt.py`, `progress.py`, `principles.md`, `moment_principles.md`, `report.py` и связанные tests. NETWORTH_SWING становится поводом для просмотра без mistake/high. В decision prompt не попадают hidden truth и агрегаты будущей драки. Исчезновение сигнала возвращает неизвестность/недостаток сравнимых данных. Принципы с недоказанной причинностью отключаются или получают честную условную формулировку. Карточка отображает имеющиеся доказательства и статус покрытия. Удалять информацию из текстового prompt недостаточно, если она остаётся в других входах.

**Приёмка:** T02–T04, T18, T20, T25–T26; regression cases исходного аудита превращены в нормальные тесты исправленного поведения. Ошибочные старые ожидания (например resolved при отсутствии leak) меняются осознанно. Не менять все assertions механически ради зелёного прогона.

**Результат:** честный legacy report с ограничениями. Не называть его новой оценкой решений.

### S1. Evidence foundation

**Цель:** версии, источники, время, неизвестность и идентичность становятся исполнимыми контрактами.

Реализовать Fact, SourceRef, TimeRef, EntityRef, Manifest и capability registry; адаптер старых данных с `implemented/unverified`. Исправить ward generations/prefix fold, pregame handling, nullable reads, frame freshness. Разобраться с raw player mapping и clock conversion на настоящем replay. Старый cache не повышать до нового качества; отделить versioned keys и атомарную валидацию.

**Приёмка:** T04–T09, T15, T27; raw/client identity/clock сверка. Если real replay недоступен, можно принять инфраструктуру и синтетические проверки, но Gate B остаётся открытым и capabilities не становятся validated.

**Результат:** проверяемый facts artifact и отчёт о поддержке/пробелах, без вымышленных нулей.

### S2. Decision dossier и интерфейс

**Цель:** пользователь видит единый выбор/границу/доказательства/причину отказа.

Реализовать Knowledge projector, DecisionBoundary, отдельные IDs, Opportunity ledger и allowlist DecisionInput. Сохранить incident index для навигации, но не передавать selection features в оценщик. Для механически неопределённых эпизодов boundary unresolved. В HTML добавить раскрываемые факты, качество данных, источники, альтернативы со статусом feasibility, отдельный outcome, статусы отсутствия клипа/истории. Пока verdict недостаточно данных, UI не должен обвинять через LLM headline.

**Приёмка:** T01–T03, T07–T08, T16–T18, T23–T25; snapshot/render проверки реальных артефактов и тесты запрещённых зависимостей между модулями. Не вводить новый frontend framework, если этой поверхности достаточно HTML/CSS/небольшого JS.

**Результат:** первый законченный сквозной evidence dossier. Его можно отдавать экспертам для разметки, но нельзя рекламировать как validated evaluator.

### S3. Спайк данных для defensive_activation.v1

**Цель:** выбрать один patch и одну пару item/ability, для которых реально проверяемы время, наблюдаемость и действие.

Собрать небольшой calibration batch реальных replay и POV; выписать raw events/properties, необходимые ограничения и критерии исключения. Проверить механику по patch-scoped источникам и клиентным наблюдениям. Подготовить рубрику с tradeoffs use/hold и альтернативными целями. Capability gaps занести как измеримые задачи, а не заполнить догадками.

**Приёмка:** Gate B для выбранного scope; точные источники и воспроизводимые traces. Если извлечение или граница окна не подтверждены — evaluator остаётся disabled. Отчёт спайка должен содержать отрицательный результат, если выбранная пара не подходит.

**Результат:** критерий, поддержанный фактами и ограничениями; либо документированное основание сменить конкретную пару, не расширяя произвольно весь пилот.

### S4. Первый оценщик и объяснение

**Цель:** реально сравнить допустимые activate/hold в одном проверенном scope.

Реализовать criterion evaluator как чистую функцию; все необходимые данные в входе, все причины в claims. Оценивать все supported opportunities, а не только смерти. Добавить строгую обработку unknown, разумных альтернатив, хороших решений и технически невозможной активации. LLM работает только с ClaimSet, значимые утверждения защищены шаблоном/валидатором. Outcome branch не может менять assessment hash.

**Приёмка:** T01–T18, Gate A–D, blinded holdout. Синтетические тесты проверяют алгоритм и границы; реальные экспертные labels проверяют качество. До прохождения Gate C допускается режим experimental dossier, а не публичное утверждение точности.

**Результат:** один работающий оценщик с явным охватом. Интеграционный запуск должен воспроизвести artifact без сети/LLM при уже имеющихся входах.

### S5. Проверяемая привычка и progress

**Цель:** одно упражнение на основе повторяющихся проверенных решений.

Реализовать HabitEvidence и CoachingPlan поверх полного ledger; examples/counterexamples; отдельные eligible/assessed/unknown; периоды и версии; rebaseline. Описательные старые метрики оставить доступными отдельно. Не мигрировать Leak HIGH как confirmed error.

**Приёмка:** T19–T21, контроль overlap/roles/patch/coverage; пользовательский comprehension pilot; изменение поведения отдельно от причинного эффекта тренера.

**Результат:** персональная проверка одной привычки без ложного «исправлено».

### S6. Расширения по данным, а не по числу экранов

После S4/S5 последовательно подключать: observation-aware карту и ward lifecycle; каталог учебных матчей; один контекстный build criterion. Для каждого — свой source/capability gate, реальные ссылки и acceptance cases. Неподключённые разделы показывают unavailable. Полноценная карта вардов с оценкой полезности требует отдельно проверить геометрию, атрибуцию информации и доступность установки.

## Согласование зависимостей

S0 можно выполнить независимо от будущей полной схемы. S1 предшествует S2. S3 может идти после минимальной части S1 параллельно с UI S2, но S4 зависит от **завершённых** S2 и S3. S5 зависит от validated assessment/ledger S4; descriptive profile можно строить раньше с соответствующей маркировкой. S6 не является условием законченности первого пилота.

Не оценивать срок S3/S4 в фиксированном числе дней до спайка: главный риск — доступность нужных событий и корректной наблюдаемости, а не объём Python-кода.

## Checklist независимого ревью Astro

1. Есть ли техническая граница World/Knowledge и запрещённые зависимости, или только текстовая инструкция?
2. Не попадают ли будущие сведения через boundary, intent, роль, candidate selection, caches или metadata?
3. Выбрана ли реальная возможность выбора и доказана ли выполнимость альтернатив? Не стала ли readiness вердиктом?
4. Инвариантны ли input/verdict/claims при смене hidden world и будущего? Проверены ли ward reuse, unknown и same-tick?
5. Не обещает ли объяснение больше критерия? Есть ли counterexamples и причины отказа прямо в render?
6. Подтверждены ли capabilities на реальных raw/client traces и независимой разметке? Есть ли корректный holdout и достаточные знаменатели?
7. Полон ли ledger, не спрятаны ли из него удачные исходы, неподдержанные случаи и ошибочные несрабатывания?
8. Не трактуется ли изменение состава/качества данных как прогресс? Не используются ли ответы модели как собственный эталон?

## Что запускать и что пока нельзя заявлять

В этом архитектурном этапе открывать `README.md` данного пакета; воспроизведения исходных дефектов запускаются обычным Python 3.12+:

```powershell
python -B docs/architecture/2026-10-05/audit_probes.py
```

Если Python не в PATH, использовать абсолютный путь к доступному интерпретатору. Скрипт не требует pytest/сети, не меняет исходники и не чинит дефекты. После исправлений его исходные наблюдения закономерно изменятся; он не заменяет новый regression suite.

Нового приложения/оценщика для запуска в этом этапе нет. Исходные CLI-команды перечислены в README проекта, но их успешность в этой среде не подтверждена. Для следующего этапа исполнитель должен дать точную фактически проверенную команду на созданный dossier и используемые входные данные.

Пока нельзя заявлять: точную видимость игрока; доказанную ошибку из смерти/нетворса/готового BKB; гарантированный лучший альтернативный исход; количественный win-probability cost; устойчивый стиль по одному матчу; исправленную привычку из исчезновения детектора; работающие рекомендации/билды/ward utility без источников. Ни архитектурный документ, ни зелёный синтетический тест не снимают эти ограничения.
