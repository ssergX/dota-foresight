# События replay, ресурсный план и независимая разметка

Дата: **7 октября 2026 года**. Продолжение инженерного этапа; полный игровой тренер ещё не аттестован.

## Реализованные потоки

`ingest/semantic_events.py` извлекает использования TP/smoke, применения и удаления их модификаторов, buyback и provider objectives. Источники разделены: trace, combat_names, provider. Sidecar проверяется по replay SHA, последовательности callback records, размерам и завершённому footer. Его record index нельзя сравнивать с индексом полного trace. Недоступный game clock не восстанавливается по будущему game start.

На публичном матче **9030822324**: 82 использования TP, 16 smoke, 3 buyback; sidecar дополнительно содержит 82 применения/82 удаления TP-модификатора и 65 применений/65 удалений smoke-модификатора. Provider дал 18 разрушений зданий, 3 убийства Roshan и 3 buyback. Записи разных источников не суммируются как уникальные игровые случаи. Снятие модификатора не устанавливает прерывание TP, прибытие или причину снятия smoke.

В отчёте появилась раскрываемая секция событий. Кнопка «История маркеров до события» строит строгую source-local проекцию `< cutoff_record_index`, разделяет caster/target и сохраняет неизвестное. Provider outcomes не допускаются в prefix. World observation не превращается в информацию игрока. Эта секция и будущие события не входят в activation notebook, ресурсный критерий или blind cases.

В собственной карточке можно задать **план следующего действия**: название, предполагаемую стоимость маны, число применений, запас и явное подтверждение. Backend считает `reserve_cost × repetitions + margin`, разницу с raw остатком после стоимости предмета и без неё. Скачанный план сохраняет match/account/action/resource hash, source records, дату и `dataset_kind`. Введённая сейчас цель не доказывает прошлое намерение; заявленная стоимость не является проверенной исторической механикой. Дефицит не становится ошибкой игрока. Неизвестные/противоречивые ресурсы отменяют расчёт; verdict=insufficient_evidence, feasibility=unknown, training_eligible=False.

`validation/review_workspace.py` создаёт **blinded/index.html** без system verdict, результата боя, чужих позиций или предыдущих ответов. Имя, проход, eligibility, verdict и version пусты. Есть проверки фактов/доступности/действий, rationale, unknowns, экспорт JSONL/POST и локальное сохранение. Extraction и decision-blinded разделены; outcome/text требуют отдельного раскрытия. Цель и точная граница выбора отсутствуют в текущем pack и не могут быть объявлены correct из него.

Приём labels связан с DatasetRecord/content hash, ограничивает references слепым контекстом, отклоняет самоприсвоенный validation и требует ссылки на последнюю версию того же reviewer/pass при исправлении. Append сериализован и атомарен. Имя/экспертность/независимость — декларации для внешнего аудита. Реальная annotations.jsonl остаётся пустой.

## Проверка и исправления

Независимый review выявил три дефекта: contextual `_known` пропускал неизвестный valid clock/legacy method/order; отдельные планы и semantic artifacts теряли тип происхождения; глубокий JSON обрывал handler. Проверяются обе временные ссылки и весь интервал свежести; dataset kind сохраняется и влияет на plan ID без зависимости от будущего; новые endpoints возвращают контролируемый 400. Все исправления покрыты regression tests.

Пройдены **652 Python tests**, **9 Go tests**, Go module verification/build. Архивы/чистая установка проверяются отдельно: актуальные результаты и SHA — `out/verification/release-readiness.json`. Тесты проверяют инженерные контракты, не качество игровых советов.

Browser QA проверила создание реального отчёта, пустой ресурсный план, явно помеченный QA сценарий, расчёт raw 691.0007 − 50 при резерве 610, историю до source-local cutoff и отсутствие system/outcome links в review workspace. QA план не является личной целью или измерением пользователя. Неисполненные из-за автоматической проверки разрешений действия не считаются успешными тестами. Первый review UI запросил отсутствующий favicon; добавлен встроенный пустой icon. Итог новых mobile/form проверок отражён отдельно в release-readiness.
