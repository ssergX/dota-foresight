# Dota Coach — фаза 3: ролевые лики (`leaks/`) — дизайн

> Дата: 2026-08-18. Продолжение фазы 2 (влита в `master`, 82 pytest).
> Предыдущие дизайны:
> `docs/superpowers/specs/2026-08-14-dota-coach-mvp-design.md`,
> `docs/superpowers/specs/2026-08-15-dota-coach-phase2-coach-design.md`.

## Цель

Расширить детектор системных ликов с 3 до 20 детекторов и сделать его **ролевым**:
пороги и сам набор применимых ликов зависят от позиции (pos1–5), серия матчей
разбирается отдельно по каждой роли.

Мотивация не «больше — лучше», а **корректность**. Текущий плоский детектор на
реальных данных одновременно выдаёт ложный лик и прячет настоящий (см. «Находки»).

Область: только слой `leaks`. Контракт с пакетом `coach/` не ломается — тренерский
бриф, ЛЛМ-промпт, петля подотчётности и рендер остаются как есть, меняется только
качество и объём входа.

## Контекст: находки на реальных данных

Проверено на 24 закешированных матчах аккаунта 182097367 (все пропарсены).

**Игрок играет три роли**, а не одну: pos3 ×10, pos4 ×11, pos5 ×3
(поле `position_est` от OpenDota; надёжность подтверждена — на pos3 ровно 0 вардов
во всех 10 играх, на pos5 в среднем 6).

Что даёт текущий плоский детектор против разбивки по ролям:

| Метрика | Смешано (сейчас) | pos3 | pos4 | pos5 |
|---|---|---|---|---|
| Обсы/игра | **2.38 → лик сработал** | 0.00 | 3.55 | 6.00 |
| Смерти/игра | **10.88 → лик сработал** | 10.0 | 11.9 | 10.0 |
| GPM-перцентиль (медиана) | 0.46 → молчит | 0.67 | **0.19** | 0.77 |

1. **Лик «мало вардов» — ложноположительный.** Сработал только потому, что десять
   оффлейн-игр с нулём вардов (корректное поведение для pos3) утащили среднее ниже
   порога 4. На саппорт-играх показатель нормальный.
2. **Смешивание ролей прячет настоящий лик.** Общая медиана GPM-перцентиля 0.46
   выглядит здоровой, при этом на pos4 перцентиль **0.19** — устойчивая системная
   дыра по золоту, невидимая текущему детектору.
3. **Сквозной реальный лик** — смерти 10–12 за игру на всех трёх ролях.

## Принципы (наследуются, не нарушать)

1. **Анти-результатничество.** `win` / `lose` / `radiant_win` не передаются в ЛЛМ
   ни в каком виде. Добавление ~20 новых полей повышает риск случайно протащить
   исход — закрывается тестом (см. «Инварианты»).
2. **Заземление.** «Как чинить» берётся из курируемой `principles.md`, а не из
   вольной памяти модели. Каждый из 20 ключей получает свою секцию.
3. **Детерминированное ядро.** Все факты считает код; ЛЛМ только формулирует.
4. **Чистые функции отдельно от сетевой склейки.**
5. **Детерминированность прогона.** На одних входных данных фокус обязан быть один
   и тот же, иначе петля подотчётности рассыпается.

## Принятые решения

| # | Решение |
|---|---|
| 1 | Пороги и набор ликов зависят от роли (pos1–5) |
| 2 | Разбор отдельный на каждую роль, а не общий по серии |
| 3 | Источник порогов — гибрид: bench / manual / personal, с явной меткой источника |
| 4 | Подача — один главный фокус на прогон + свёрнутый список «тоже видно» |
| 5 | Окно 50 матчей; роль разбирается от 5 игр, иначе «данных мало» |
| 6 | `principles.md` — секция под каждый из 20 ключей |
| 7 | v1 = 20 детекторов T1; 6 детекторов T2 вынесены за область |

## Архитектура

`leaks.py` (83 строки, три захардкоженных детектора, плоские пороги) превращается
в пакет. Один файл — одна ответственность.

```
src/dota_coach/leaks/
  __init__.py        — фасад: detect_leaks(matches, account_id) -> list[Leak]
  roles.py           — определение роли матча, сегментация серии по ролям
  thresholds.py      — гибридные пороги: bench | manual | personal
  severity.py        — нормализация превышения, ранжирование, дедуп по семьям
  registry.py        — реестр детекторов (декоратор + выборка по роли)
  detectors/
    __init__.py      — импорт всех модулей ради регистрации
    laning.py  economy.py  deaths.py  fights.py  vision.py  objectives.py
```

### Детектор — чистая функция с метаданными

```python
@detector(
    key="lane_collapse",
    title="Проваленный лейн",
    roles=(1, 2, 3),                     # где применим
    requires=("lane_efficiency_pct",),   # поля → авто-деградация
    impact=0.8,                          # вес важности для severity
    phase="laning",
    family="laning",                     # для дедупликации
)
def lane_collapse(rows: list[Row], role: int, th: Thresholds) -> Leak | None: ...
```

Что это даёт:

- детектор не запускается на роли, где бессмыслен (варды для pos3);
- при отсутствующих полях матч **исключается из выборки детектора**, а не считается
  нулём;
- добавление 21-го детектора — один новый файл-функция, без правки общего кода.

### Поток данных

```
matches → segment_by_role() → {3: [...], 4: [...], 5: [...]}
                                    │
                    для каждой роли с >= 5 играми:
                       registry.applicable(role) → детекторы
                            └→ фильтр матчей по requires
                                 └→ thresholds.for(role, metric) → (value, source)
                                      └→ Leak(role, severity, source, sample_size)
                                            │
                    все лики → severity.rank() → фокус + «тоже видно»
                                            │
                                        coach/ (контракт не меняется)
```

### Определение роли

`position_est` — основной источник. Фолбэк при отсутствии: `lane_role` + `is_roaming`
(`lane_role=1` → pos1/pos5, `2` → pos2, `3` → pos3/pos4; уточнение по `obs_placed`).
Матч без определимой роли исключается из сегментации и попадает в строку покрытия.

### `Leak` — новые поля

```python
@dataclass
class Leak:
    key: str
    title: str
    magnitude: str
    example_matches: list[int] = field(default_factory=list)
    confidence: Confidence = Confidence.LOW
    metric: str = ""
    value: float = 0.0
    threshold: float = 0.0
    direction: str = "lower_is_better"
    # новое:
    role: int | None = None              # позиция, внутри которой найден лик
    source: str = "manual"               # bench | manual | personal
    sample_size: int = 0                 # матчей после фильтра requires
    severity: float = 0.0                # [0..1], для ранжирования
    phase: str = ""                      # laning | economy | deaths | fights | vision | objectives
    family: str = ""                     # для дедупликации в списке «тоже видно»
```

## Пороги: гибридная модель

`thresholds.py` отдаёт пару `(value, source)`:

- **`bench`** — перцентиль из блока `benchmarks` ответа OpenDota (10 метрик:
  `gold_per_min`, `xp_per_min`, `kills_per_min`, `last_hits_per_min`,
  `denies_per_min`, `hero_damage_per_min`, `hero_healing_per_min`,
  `assists_per_min`, `deaths_per_min`, `tower_damage`). Порог — перцентиль 0.4.
  Оговорка: бенчмарки считаются **по герою**, а не по роли; ролевая специфика
  учитывается через `roles` детектора, а не через сам бенчмарк.
- **`manual`** — константа, заданная под конкретную роль. Все ручные константы
  живут в одном месте (`thresholds.py`), а не размазаны по детекторам.
- **`personal`** — личный базлайн для петли прогресса: сравнение текущего окна с
  сохранённым в истории. Не используется для срабатывания лика, только для
  формулировки «стало лучше/хуже».

Метка `source` доезжает до брифа: тренер говорит «ниже 20% игроков на этом герое»
там, где порог из бенчмарка, и «ниже разумной планки», где он ручной.

## Severity и выбор фокуса

```
severity = normalized_excess * impact * sample_confidence
```

- **`normalized_excess`** — приведение к [0..1]. Для bench-порогов это разница прямо
  в перцентильном пространстве (`threshold - value`). Для ручных — относительное
  превышение `|value - threshold| / threshold`, обрезанное сверху до 1.0.
- **`impact`** — вес важности из декоратора. Феединг весит больше, чем «не берёт
  руны», при равном превышении.
- **`sample_confidence`** — растёт от 5 игр (минимум) до 1.0 к 12 играм. Не даёт
  экстремальному отклонению на 5 играх перебить устойчивую проблему на 11.

**Детерминированность.** При равной severity — тай-брейк по `key` в алфавитном
порядке. Фокус не должен прыгать между прогонами на одних данных.

**Дедупликация по семьям.** На реальных данных разом сработают `feeding`,
`time_dead`, `early_deaths`, `repeat_victim` — одна проблема в четырёх проекциях.
В список «тоже видно» идёт **не более одного лика на `family`** — сильнейший по
severity. Остальные члены семьи фокуса передаются в бриф как подтверждающие детали,
а не как отдельные пункты.

## Деградация на непропарсенных матчах

Богатые поля (`gold_t`, `lh_t`, `obs_log`, `life_state_dead`, `lane_efficiency_pct`,
`teamfight_participation`, `stuns`, `purchase_log`) существуют только у пропарсенных
матчей. Базовые (K/D/A, GPM, XPM, ластхиты, денаи, урон, нетворс, предметы) есть
всегда.

Правила:

1. `requires` фильтрует матчи **для конкретного детектора**, а не для всей серии.
2. Отсутствующее поле означает исключение матча, **никогда не подстановку нуля**.
3. Если после фильтра осталось < 5 матчей — детектор не запускается.
4. У разных детекторов разный `sample_size`; он честно доезжает до
   `sample_confidence`.
5. В отчёт идёт строка покрытия: «по лику X данных хватило на N из M матчей».

## Интеграция с `coach/`

Контракт не ломается, правки точечные:

- **`coach.py`** — вместо «первый лик из списка» берёт топ-1 по `severity`.
- **`history.py`** — начинает сохранять **все** сработавшие лики, а не только фокус
  (иначе прогресс по остальным метрикам не померить). Формат истории версионируется;
  старые записи читаются как есть.
- **Переименование `low_warding` → `low_obs`.** Старые записи истории содержат ключ
  `low_warding`, и без обработки петля прогресса по этому лику разорвётся. При чтении
  истории ключ мапится на новый. Отдельно: старый `low_warding` считался по всей
  серии без роли, поэтому его историческое значение несравнимо с новым ролевым —
  сравнение прогресса для этого ключа начинается заново, о чём тренер говорит явно.
- **`progress.py`** — работает без изменений (сравнение по метрике фокуса).
- **`prompt.py` / `brief.py`** — в промпт добавляются роль, `source` порога и
  подтверждающие детали семьи фокуса. Схема структурного ответа ЛЛМ не меняется.
- **`report.py`** — свёрнутый блок «тоже видно» + строка покрытия.

## Инварианты (закрыты тестами)

1. **Анти-результатничество.** Тест сканирует сериализованный промпт и объекты
   `Leak` на ключи `win`, `lose`, `radiant_win`, `radiant_score`, `dire_score` —
   их не должно быть.
2. **Полнота базы принципов.** Тест проверяет, что для каждого зарегистрированного в `registry` ключа в `principles.md` есть секция. Generic-заглушка допустима
   только как аварийный фолбэк.
3. **Детерминированность.** Двойной прогон `detect_leaks` на одних данных даёт
   идентичный порядок и идентичный фокус.
4. **Целостность метаданных.** У каждого лика непустые `metric`, `threshold`,
   `source`, `sample_size`.

## Приёмка на реальных данных

24 закешированных матча аккаунта 182097367 — регрессионные фикстуры с известными
правильными ответами:

1. `low_obs` **не срабатывает** на pos3 — текущий ложный лик обязан исчезнуть.
2. `farm_below_bracket` **срабатывает** на pos4 (перцентиль 0.19) — сейчас прячется,
   обязан появиться.
3. Лики семьи `deaths` срабатывают на всех трёх ролях (10–12 смертей за игру).
4. pos5 с 3 играми **не разбирается** — выдаётся «данных мало», а не диагноз.
5. В списке «тоже видно» не больше одного лика семьи `deaths`.

Пункты 1 и 2 — прямая проверка, что ролевая сегментация отработала.

## Порядок работ

0. Откатить сломанный `leaks.py` в рабочем дереве (лишний отступ на первой строке,
   SyntaxError) — без этого ничего не импортируется.
1. Расширение `normalize.py` + новые поля `Leak`.
2. Каркас пакета: `registry`, `roles`, `thresholds`, `severity`.
3. Детекторы по группам: `deaths` → `laning` → `economy` → `vision` → `fights` →
   `objectives`.
4. Интеграция с `coach/` (`coach.py`, `history.py`, `prompt.py`, `report.py`).
5. `principles.md` — 20 секций.
6. CLI `--n 50`.
7. Живой прогон на 50 матчах + сверка с критериями приёмки.

## Вне области (отложено осознанно)

- **6 детекторов тира T2** — требуют кросс-референса таймкодов с окнами
  `teamfights`/`objectives` или базы таймингов предметов: `roam_no_result`,
  `item_timing_late`, `deaths_out_of_fights`, `dives_first_dies_first`,
  `no_vision_pre_objective`, `no_objective_conversion`. Пороги заведомо ручные и
  шумные; делать после того, как T1 покажет вменяемый результат на живых данных.
- **Автозаказ парса** (`POST /request/{match_id}` для непропарсенных) — добавляет
  асинхронность и ожидание. Решать после замера, насколько дырявые свежие матчи.
- **RAG вместо `principles.md`** — исходная идея фазы 2.5. Курируемая база из 20
  секций закрывает потребность на текущем масштабе; RAG имеет смысл, когда база
  вырастет за пределы, помещающиеся в промпт.
- **Разбор одного матча** остаётся как есть (`analyze`), ролевые лики его не
  касаются.
