# Дизайн: Dota Coach (личный AI-тренер) — MVP

- **Дата:** 2026-08-14
- **Статус:** Draft (на ревью)
- **Автор:** cerg + Claude (брейншторм)

## 1. Цель

Личный пост-матч инструмент, который по записанным играм пользователя в Dota 2:

- находит **системные лики** — повторяющиеся контролируемые ошибки — по многим матчам;
- **оценивает качество решений** по входным данным, а не по исходу (не результатничает);
- показывает ключевые моменты **прыжком в видеозапись** матча + подписью.

Первичная цель — стать сильнее в игре. Пользователь — юзер №1; продуктовизация вне скоупа (сначала проверяем ценность на себе).

## 2. Не-цели (YAGNI)

- Не реалтайм / не оверлей во время игры.
- Не покадровый CV-детектор событий — события берём из распарсенного реплея.
- Не «скопируй клип прошника» (пространство состояний слишком велико для инстанс-ретрива).
- Не конкурент STRATZ по сырой статистике.
- Не мультиюзер, не биллинг, не паблик-деплой.

## 3. Ключевые принципы (зафиксировано в брейншторме)

1. **Гибрид данные + видео + ЛЛМ.** Данные находят *где/что* (события с таймкодом), видео показывает картинку, ЛЛМ формулирует «как надо».
2. **Решение ≠ результат.** Оцениваем по знаемой на момент решения инфе. Готовы вернуть вердикт «норм заход, вария» — тул, который иногда говорит «не меняй», ценнее того, что ругает каждую смерть.
3. **Центр тяжести — межматчевые паттерны.** Единичный матч = анекдот; распределение по многим играм = сигнал. Главная ценность — детектор системных ликов.
4. **Приоритет контролируемых повторяющихся ликов** над геройскими one-off моментами.
5. **Метка уверенности на каждом выводе.** Измеримое (бенчмарк, вижен, байбек) — высокая; агрессивные колы — низкая, подаём как «сам глянь».
6. **Опора на «идеал» — трёхслойная** (см. §7): бенчмарки → принципы → тенденции хай-ммр.
7. **ЛЛМ обязана привязывать вывод к датапоинту** из game-state; недостаточно инфы → говорит об этом, а не выдумывает.

## 4. Архитектура

Поток данных: `match_id (+ video) → отчёт`. Каждый модуль — отдельная единица с чёткой границей; остальные не знают про источник данных.

1. **`ingest`** — получить распарсенный матч.
   - Вход: `match_id` (или `account_id` → список последних матчей).
   - Источник: OpenDota API (публичные распарсенные матчи; при необходимости — запрос парса). Опционально Stratz (GraphQL, богаче позиционка) и/или локальный парс `.dem`.
   - Выход: нормализованная модель матча (единый формат событий/рядов).

2. **`events`** — извлечь события-кандидаты с игровым таймкодом.
   - Тимфайты (`teamfights[]`: start/end, deaths, per-player gold/xp/damage).
   - Смерти (`kills_log`), объективки (`objectives[]`: Рошан / тавера / бараки / первая кровь).
   - Свинги нетворса (из `gold_t[]` / `xp_t[]`).
   - Тайминги предметов (`purchase_log`).
   - Вардинг (`obs_log` / `sen_log` — время + координаты).

3. **`benchmarks`** — перцентили ранга/героя.
   - Источник: OpenDota benchmarks (CS@10, GPM, XPM, урон, смерти и т.п.).
   - Выход: для каждой измеримой метрики — твоё значение + перцентиль эталона.

4. **`scoring`** — ранжировать события по «полезности для прокачки».
   - Скор = f(импакт, твоя вовлечённость, сигнал-ошибки, отклонение от бенчмарка).
   - Классификация решения: `mistake` / `fine-variance` / `not-enough-info`.
   - Дедуп (не тащить N событий из одной драки) → топ 8–12.
   - Каждый вывод несёт метку уверенности.

5. **`leaks`** — агрегатор по многим матчам (главная ценность).
   - Вход: серия распарсенных матчей.
   - Считает распределения: success-rate дайвов, TP-дисциплина, тайминг ключевого айтема vs бенчмарк и т.п.
   - Выход: топ системных ликов с величиной и примерами-моментами.

6. **`video_align`** — привязать игровое время к таймкоду видео.
   - OCR часов с HUD → `offset = t_video − t_game`.
   - Периодический ре-синк для пауз.
   - API: по игровому времени вернуть `t_video`; вырезать клип; семплировать N кадров окна.

7. **`coach`** *(фаза 2)* — AI-разбор.
   - Собирает «game-state пакет» момента (герой / уровень / предметы / кулдауны / позиция / вижен / враги рядом / бенчмарк / исход драки) + опц. кадры.
   - Промпт с правилом привязки к датапоинтам + курированная база принципов.
   - Verify-проход: второй вызов проверяет совет на адекватность.
   - Модель: Sonnet/Haiku, prompt caching, опц. Batch.

8. **`report`** — локальный отчёт.
   - Таймлайн кликабельных моментов (клик → видео на `t_video`) + подпись + метка уверенности.
   - Блок системных ликов (из `leaks`).
   - **MVP: статический HTML** (проще). FastAPI+HTMX — только если понадобится интерактивность.

## 5. Скоринг (детали)

Факторы:

- **Импакт** — |свинг голда/xp| в драке; ценность объективки; флип игры.
- **Вовлечённость** — ты актор? умер? наносил/получал урон? (твои события весят больше).
- **Сигнал-ошибки** (эвристики) — соло-смерть, пока команда в другом месте; смерть в тумане / без варда; непрожатый большой кулдаун; слитый тавер-пуш; нулевое участие в выигранной драке; байбек не использован у объективки.
- **Отклонение от бенчмарка** — метрика на момент vs перцентиль ранга/героя.

**Анти-результатничество.** Для флагнутого события, где есть данные о входе (ресурсы, видимые ресурсы врага, кулдауны, бэкап, вижен), классифицируем `mistake` / `fine-variance` / `not-enough-info`. Порог «сколько нужно было» берётся из слоя-3 опоры (фаза 3); до этого — из грубых эвристик с низкой уверенностью.

## 6. Выравнивание видео (детали)

- Регион HUD-часов фиксирован (верх по центру); кадрируем → OCR (paddleocr/tesseract).
- Считываем в нескольких точках видео → надёжный offset; расхождение = пауза/пропуск → ре-синк.
- Формат записи: любой mp4 (OBS / GeForce / встроенная запись). Требование — виден игровой таймер.

## 7. Опора на «как надо» — три слоя

1. **Бенчмарки (MVP).** Перцентили ранга/героя + распределения билдов/таймингов из OpenDota. Объективный «идеал» для измеримого, без ЛЛМ.
2. **Принципы + RAG (ф2).** Курированная база теории (вижен, смоук, менеджмент волны, окна пауэр-спайков), ретрив под тип ситуации.
3. **Тенденции хай-ммр (ф3).** Дата-пайплайн: парс многих реплеев Immortal/хай-ммр (Stratz) → извлечение фич → агрегат «класс ситуации → что делают сильные». Даёт калиброванные приоры (порог EV). Ориентир — сильные пабы на 1–2 ранга выше; прошники для концептов/таймингов (про-макро в пабе бывает вредно).

## 8. Фазы

- **MVP (ф1):** `ingest`, `events`, `benchmarks`, `scoring`, `leaks`, `video_align`, `report`. Без ЛЛМ → $0 на инференс. Результат: топ-моменты с прыжком в видео + системные лики vs бенчмарк.
- **Ф2:** `coach` (AI-разбор) + база принципов + RAG.
- **Ф3:** дата-пайплайн тенденций хай-ммр (слой-3 опоры) + EV-пороги.

## 9. Стоимость инференса (ф2)

Порядково на матч (~40 мин):

| Вариант | Что жрёт токены | Цена/матч |
|---|---|---|
| A / MVP | LLM не вызывается | $0 |
| B текстом | данные матча (~15K вход) | ~$0.03–0.15 |
| B + vision по ключевым моментам | ~30–40 кадров (~70K вход) | ~$0.10–0.45 |
| C (whole-video vision) | ~1000+ кадров (~1.8M) | ~$5–9 — **не берём** |

Удешевители: Sonnet/Haiku вместо Opus, prompt caching (~−90% на фикс-префиксе), Batch API (−50%).

## 10. Стек и предпосылки

- Python 3.12, Windows.
- OpenDota API (free), опц. Stratz (нужен API-ключ).
- Видео/OCR: opencv, paddleocr/tesseract, ffmpeg.
- Отчёт: статический HTML (MVP).
- ЛЛМ (ф2): Anthropic SDK, `claude-sonnet-5` / `claude-haiku-4-5`.
- От пользователя: Steam/Dota account ID (публичные матчи), mp4-запись с видимым таймером.

## 11. Риски

- Главные риски **не технические**: дистрибуция (если продуктовизировать), ретеншн, качество совета.
- Приватность: OpenDota видит только публичные матчи — нужен «Expose Public Match Data» в настройках Dota.
- OCR часов может врать при нестандартном разрешении/HUD-моде — заложить калибровку региона.
- Позиционка ограничена у OpenDota (для «стоял слишком глубоко» нужен Stratz / локальный парс).

## 12. Критерии успеха MVP

- По одному матчу: отчёт с 8–12 ранжированными моментами; клик → видео прыгает в нужную секунду (±1–2 с).
- По серии из ~20 игр: список из 2–3 системных ликов с числами и примерами-клипами.
- Ни один вывод не является чистым результатничеством: у каждого есть метка уверенности или вердикт «вария».

## 13. Открытые вопросы

- Точный набор эвристик «сигнал-ошибки» — итерируем на реальных матчах.
- Нужен ли локальный парс `.dem` в MVP или хватит OpenDota — по умолчанию OpenDota; локальный парс подключаем, если не хватит позиционки.
- Формат хранения серии матчей для `leaks` (просто JSON-кэш vs SQLite) — решаем при реализации, склоняемся к SQLite.
